# MACHIDA FOOD データベース設計（Phase 1）

- 作成日：2026年11月3日
- 対象：Supabase（PostgreSQL）
- SQL：`supabase/migrations/20261103000000_phase1_init.sql`
- 初期データ：`supabase/seed.sql`（デモ用の架空5店舗）
- テスト：`bash scripts/test-db.sh`（使い捨てのローカルDBで24項目のアクセステストを実行。本番には接続しない）

---

## 1. 設計の考え方

1. **すべてのテーブルでRLS（行単位のアクセス制御）を有効にする。** テストで全テーブルを機械的に確認している（T21）。
2. **後から増える中身はデータとして持つ。** 店舗、メニュー、予算別プラン、クーポン、ランク、称号、枠、衣装、各種ポイント数（`app_settings`）は、管理画面から追加・変更できる。プログラムの修正は不要。
3. **不正が起きやすい操作は関数（RPC）だけで行う。** スタンプ・ポイント・クーポン利用・空席更新・会員登録は、画面からテーブルを直接書き換えられない。関数の中で権限を確認し、二重付与は**データベースの一意制約**で止める。
4. **ポイントは残高を持たず、増減の記録を積み上げる**（`point_ledger`）。あとから「なぜこの残高か」を必ず説明できる。
5. **すべての付与・利用を記録する**（`audit_logs`）。同じ日の2回目のスタンプやクーポンの再利用の試みも記録し、不正の監視に使う。
6. **ログイン方法と会員情報を切り離す。** 会員情報（`profiles`）はSupabaseのログイン（`auth.users`）とidでつながるだけなので、後からLINEやGoogleのログインを足しても同じ会員として引き継げる。
7. **将来のMACHIDA NIGHTに備える。** 店舗には `brand`（food / night）を持たせている。NIGHTの利用者データは、PROJECT_BRIEFの方針どおり別のSupabaseプロジェクトに分ける前提。

## 2. 役割と見える範囲

| 役割 | 判定方法 | できること |
|---|---|---|
| 未ログイン | — | 掲載中の店舗・メニュー・予算別プラン・空席・通常クーポンを見る |
| 会員（user） | `profiles` がある | 自分のプロフィール・ポイント・スタンプ・クーポンを見る。ニックネーム・誕生月・装備を変える。会員証QRを発行する |
| 店舗スタッフ（store_staff） | `store_members` | 自店の会員証を読み取ってスタンプ・クーポンを処理、空席更新、限定メニュー・タイムセールの登録、自店の利用記録を見る |
| 店舗オーナー（store_owner） | `store_members` | スタッフの権限＋自店の店舗情報・営業時間・メニュー・予算別プラン・席の種類・クーポンの編集 |
| 運営管理者（admin） | `admins` | すべて。店舗の掲載承認（掲載状態は運営だけが変えられる） |

店舗のスタッフにも、会員の名前や誕生月などの**プロフィールは見せない**（自店での来店・クーポン利用の記録だけ）。

## 3. テーブル一覧

### 店舗まわり

| テーブル | 内容 |
|---|---|
| `areas` | エリア（町田駅北口・原町田・中町・森野…）。市全域・周辺地域へ増やせる |
| `stores` | 店舗。ジャンル、予算の目安、最大人数、支払い方法、こだわり条件、駐車場、スタンプの目標数と特典、掲載状態 |
| `store_members` | 店舗のオーナー・スタッフ |
| `store_hours` | 曜日ごとの営業時間とL.O.（1日に複数行でランチ・ディナーに対応。行がない曜日は定休日） |
| `store_closed_days` | 臨時休業日 |
| `menu_items` | メニュー（税込み） |
| `daily_specials` | 今日の限定メニュー（日付つき） |
| `budget_plans` | 予算別プラン（予算・料理○品・ドリンク○杯・お通し／席料の扱い） |
| `seat_types` | 席の種類ごとの総数と空き（空きは席数を超えられない） |
| `store_seat_status` | 満席時の待ち時間と最終更新時刻 |
| `time_sales` | タイムセール（開始・終了時刻） |
| `coupons` | クーポン（通常・雨の日・初回登録特典・ポイント交換用） |

### 会員まわり

| テーブル | 内容 |
|---|---|
| `profiles` | ニックネーム、誕生月、20歳以上の確認日時、規約同意日時、装備中の称号・枠・衣装 |
| `point_ledger` | 町田ポイントの増減の記録 |
| `ranks` | ランク（名前・動物・必要ポイント・ポイント倍率・招待制か） |
| `cosmetics` | 称号・枠・衣装（ランクで解放されるもの、初回登録で配るもの） |
| `user_cosmetics` | 会員が手に入れた称号・枠・衣装 |
| `user_coupons` | 特定の会員に配られたクーポン（初回登録特典など） |
| `coupon_redemptions` | クーポンの利用記録（**1人1回を一意制約で保証**） |
| `stamps` | 来店スタンプ（**1店舗1日1回を一意制約で保証**） |
| `stamp_rewards` | スタンプがたまって発行された特典 |
| `member_tokens` | 会員証QRの使い捨て番号（30秒で失効、個人情報なし。画面からは読めない） |
| `store_pin_secrets` | 店舗PINの元になる秘密の値（画面からは読めない。作り直しで更新） |
| `favorites` | お気に入り |
| `audit_logs` | 付与・利用・空席更新などの操作の記録 |
| `app_settings` | ポイント数、会員証QRの有効秒数などの設定値 |
| `admins` | 運営管理者 |

ビュー：`my_points`（ポイント残高と累計獲得）、`my_stamp_cards`（お店ごとのスタンプカード）。どちらも見る人の権限で絞られる。

## 4. 画面から呼ぶ関数（RPC）

| 関数 | 呼ぶ人 | 内容 |
|---|---|---|
| `register_profile(ニックネーム, 誕生月, 20歳以上か, 規約同意)` | 会員 | 会員登録と初回登録特典（500pt・初回来店クーポン・コック衣装）。何度呼んでも特典は1回 |
| `issue_member_token()` | 会員 | 会員証QRの番号を発行（30秒） |
| `redeem_visit(番号, 店舗)` | 店舗スタッフ | 来店スタンプとポイント（来店50pt×ランク倍率、初めてのお店+100pt、はしご+80ptは20歳以上の確認者のみ）。スタンプが目標数に達したら特典を発行 |
| `redeem_coupon(番号, クーポン)` | 店舗スタッフ | クーポンを使用済みに（期間・枚数制限・配布対象を確認、+10pt） |
| `update_seats(店舗, 席ごとの空き, 待ち時間)` | 店舗スタッフ | 空席の更新 |
| `store_pin_today(店舗)` | 店舗スタッフ | 今日の店舗PIN（4桁・毎日変わる）を表示 |
| `rotate_store_pin(店舗)` | オーナー・運営 | 店舗PINを作り直す |
| `redeem_visit_by_pin(店舗, PIN)` | 会員（スタッフが入力） | 予備の来店認証。スタッフがお客様のスマホにPINを入力してスタンプ。1人・1店舗・1日5回失敗で停止 |
| `delete_my_account()` | 会員 | 退会（アカウントと会員データを削除。操作の記録は残す。店舗・運営のアカウントは不可） |

ランクは `rank_of()` で累計獲得ポイントから決まり、交換でポイントを使っても下がらない。招待制のブラックはポイントでは到達しない。

## 5. テストで確認していること（24項目・すべて合格）

| No. | 内容 |
|---|---|
| T01–T02 | 未ログインでは掲載中の店舗と通常クーポンだけが見え、付与の関数は呼べない |
| T03 | 初回登録特典は1回だけ |
| T04 | 会員はポイントや記録を直接書き換えられず、規約同意日時も変えられない |
| T05, T20 | 持っている（ランクで解放された）称号・枠・衣装だけ装備できる。招待制ランクのものは不可 |
| T06 | 会員証QRの番号の表は画面から読めない |
| T07 | 他の会員のプロフィール・ポイント・クーポンは見えない |
| T08 | 来店スタンプは1店舗1日1回 |
| T09 | スタッフは他店で付与できず、他店の記録・会員のプロフィールも見えない |
| T10 | 期限切れの会員証QR（スクリーンショットの使い回し）は使えない |
| T11 | クーポンは1人1回 |
| T12 | スタッフは自店の限定メニューだけ登録でき、メニュー価格や他店は変えられない |
| T13 | 空席は自店だけ更新でき、席数を超える値は入らない |
| T14 | 操作の記録が残り、スタッフには自店の記録だけが見える |
| T15–T16 | オーナーは自店の情報だけ更新でき、掲載状態は運営だけが変えられる |
| T17 | はしごボーナスは20歳以上の確認をした会員だけ |
| T18 | 配られていない初回クーポンは使えない |
| T19 | ランクは累計獲得ポイントで決まり、交換しても下がらない |
| T21 | public のすべてのテーブルでRLSが有効 |
| T22 | トリガー専用の関数は画面から呼べず、すべての関数の search_path が固定されている |
| T23 | 退会は本人だけ・関連データも削除・記録は残る・店舗アカウントは自分で退会できない |
| T24 | 店舗PINはその店の人だけが見られ、毎日変わり、間違いは記録・5回で当日停止、オーナーが作り直せる |

わざと会員情報を誰でも見える設定に壊すと、T07で失敗して止まることも確認済み。

## 6. Phase 2 以降で追加するテーブル（予定）

既存のテーブルを変えずに、新しいマイグレーションとして追加できる形にしている。

| 機能 | 追加予定 |
|---|---|
| 予約 | `reservations`（リクエスト→承認／お断り／キャンセル、無断キャンセルの記録） |
| 順番待ち | `waitlist_entries`（受付番号・人数・状態・呼び出し時刻） |
| みんなで決める投票 | `polls`、`poll_options`、`poll_votes`（未登録の友達はリンクの番号で投票） |
| スタンプラリー | 来店記録（`stamps`）から集計するため、ラリーの定義 `rallies`・`rally_stores` を追加するだけ |
| お知らせ | `notifications`（LINE連携は外部サービスの設定後） |
| ポイント交換・ミッション | `exchange_items`、`missions`、`mission_claims` |
| 人気メニュー投票 | `menu_votes`（来店記録がある人のみ） |

## 7. 本番に入れる前に必要なこと

- Supabaseのアカウントとプロジェクトの作成（ご本人の手続き）
- 本番では `supabase/tests/` の中身（テスト用の準備・テスト用の利用者）は**実行しない**
- 20歳以上の確認は現在「自己申告」。より確実な確認方法が必要かは、運営方針として判断する
- 期限切れの会員証QRの番号の片付け（定期実行。pg_cron 等）を追加する
- 会員証QRの発行回数の制限（短時間に大量発行させない）は、画面側とSupabaseの設定で追加する
- 雨の日クーポンの「雨かどうか」の判定は、天気APIの選定後に関数へ追加する
